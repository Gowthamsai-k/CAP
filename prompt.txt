6. Multi-agent architecture
This is the central AI component and the main focus of your research.

Do not create agents that merely repeat the same LLM call with different prompts. Each agent needs a clearly defined responsibility, structured input, structured output, and validation rules.
Agent 1: Query Understanding Agent
Responsibilities:
- Understand user intent.
- Identify the compliance domain.
- Identify all relevant countries.
- Identify relevant industries.
- Determine the requested task.
- Identify whether company documents are required.
Example input:
Can we transfer employee data from Germany to India
while complying with both countries' privacy laws?


Expected output:
{
  "intent": "cross_border_compliance",
  "jurisdictions": ["DE", "IN"],
  "domains": ["data_privacy"],
  "industry": "general",
  "requires_legal_kb": true,
  "requires_company_kb": false,
  "requires_comparison": true,
  "requires_risk_assessment": true
}


Agent 2: Retrieval Planning Agent
Converts the query understanding into a structured retrieval plan.

Example:
{

    {
      "jurisdiction": "DE",
      "domain": "data_privacy"

    {

      "domain": "data_privacy"

  "company_search": null,
  "document_status": ["active"],
  "search_strategy": "hybrid"
}


Important: use a Pydantic schema with enumerated values and backend validation. The LLM must never execute arbitrary database filters or bypass access controls.
Agent 3: Jurisdiction Retrieval Agents
Execute searches independently for each jurisdiction.

For example:

Each agent returns:
- Relevant legal sections.
- Source document.
- Section identifiers.
- Source URL.
- Effective-date information.
- Retrieval score.
- Supporting text.
Do not assume a separate LLM is necessary for every country. Specialized retrieval workers can use the same retrieval implementation with different jurisdiction filters.
Agent 4: Company Document Retrieval Agent
Only activated when the question requires organization-specific information.

Retrieves:
- Internal policies.
- Contracts.
- SOPs.
- Company-specific procedures.
Must enforce:
- Authenticated user.
- Organization membership.
- Company ID.
- Document-level permissions.
- Tenant isolation.
Agent 5: Evidence Aggregation Agent
Combines the results from different retrieval workers.

Responsibilities:
- Remove duplicates.
- Group evidence by jurisdiction.
- Identify missing evidence.
- Identify contradictory provisions.
- Preserve source provenance.
- Rank evidence using relevance and authority.
Do not simply discard lower-ranked evidence based on a single similarity score.
Agent 6: Compliance Reasoning Agent
This is the main reasoning component.

It receives:
- User question.
- Legal evidence.
- Company evidence, if relevant.
- Jurisdiction context.
- Document version and effective-date information.
It determines:
- Applicable legal obligations.
- Whether company policies appear to satisfy them.
- Potential gaps.
- Exceptions and dependencies.
- Areas requiring human legal review.
Every finding must be linked to specific supporting evidence.
Agent 7: Critic / Adversarial Agent
This agent independently challenges the proposed result.

It should ask:
- Is there a missing regulation?
- Is the evidence from the correct jurisdiction?
- Is the cited provision applicable on the relevant date?
- Are there exceptions?
- Is there contradictory evidence?
- Is the answer making unsupported assumptions?
- Has the reasoning confused guidance with binding legislation?
If a material issue is detected, trigger another retrieval or reasoning cycle.

Set a maximum retry limit to prevent infinite loops.
Agent 8: Citation Verification Agent
This agent verifies that:
- Each factual legal claim has supporting evidence.
- The cited section exists.
- The quoted text matches the stored source.
- The source is authoritative enough for the claim.
- The cited version is applicable to the requested date.
- No unsupported legal claims remain.
Prefer deterministic backend verification for source IDs, section IDs, quotations, and document versions. Use an LLM for semantic support assessment, not as the sole proof of citation validity.
Agent 9: Risk Assessment Agent
Classifies potential issues:
- Critical
- High
- Medium
- Low
- Unknown / Insufficient evidence
Each risk should include:
{
  "risk_id": "RISK_001",
  "severity": "high",
  "description": "Potential data retention compliance gap",
  "company_evidence": [],
  "legal_evidence": [],
  "reason": "Explanation of the identified gap",
  "recommended_action": "Review and update the retention policy",
  "requires_human_review": true
}


Risk severity should be based on a transparent, configurable methodology. Do not present an LLM-generated risk score as a statistically validated probability.

Change detection methods
Implement in this order:
1. HTTP ETag.
2. Last-Modified header.
3. SHA-256 content hash.
4. Parsed-text comparison.
5. Section-level semantic diff.
Not every government source supports all of these.

When metadata is missing or unreliable, fall back to content comparison.
Version management
Never simply overwrite an old legal document.

Maintain:
- Original source.
- Original downloaded file.
- Parsed content.
- Content hash.
- Version number.
- Publication date.
- Effective date.
- Retrieval/indexing status.
- Superseded or repealed status.
A legal provision may be published on one date but become effective later. Your system must distinguish these dates.
Incremental indexing
If only one section changes:
Old Document
    |
    +-- Section 1 (unchanged)
    +-- Section 2 (changed)
    +-- Section 3 (unchanged)
    +-- Section 4 (unchanged)


Only reprocess the affected section and its dependent chunks.

Maintain links between old and new versions so historical queries remain reproducible.
Source discovery
For your initial implementation, support manually registered official URLs and document uploads.

Later, add an optional discovery workflow when a user asks about an unsupported jurisdiction.

The discovery agent must:
- Find a candidate source.
- Verify the publisher and jurisdiction.
- Identify the document type.
- Validate the document's relevance.
- Require approval or apply predefined source-trust rules before indexing.
Do not let an unrestricted web crawler ingest arbitrary content into the legal knowledge base.
